What was actually run

WeKnora v0.8.2 stayed up in Docker (app, ParadeDB, Redis, docreader, UI). Ollama on this machine served nomic-embed-text (768-d) and qwen2.5:0.5b. Eleven documents were ingested through POST /api/v1/knowledge-bases/:id/knowledge/manual and parsed to completed.

  • Public READMEs: habla-spanish, orbitdiff, mstudios-react, hermes-agent, logo-creation-skill, betterbrand-breath-test, tech-demos.
  • Public GitHub profile card for deserteaglemj (created 2024-12-11, 7 public repos).
  • Files already in this workspace: AGENTS.md and tracking/seen-bookmarks.json.
  • A calendar digest built from the primary Google Calendar (Sep 2026). Third-party email addresses are omitted from this brief.

Each question was sent to POST /knowledge-bases/:id/hybrid-search five times after the index and embedding model were warm. A hit means every expected string was inside the returned chunks. The Cursor baseline is rg -F over /workspace, excluding node_modules and dist.

Install fact that blocked the first index. WeKnora rewrites 127.0.0.1 to host.docker.internal and refuses that host until it is on SSRF_WHITELIST_EXTRA. Ollama also has to listen on 0.0.0.0, because the rewritten address is the Docker bridge (172.17.0.1), not the host loopback. Until that was fixed, every document failed with connection refused and search returned nothing.

Median warm hybrid search across the 11 real questions: 58.7 ms. Keyword-only search (vectors off) hit the same 11/11 at a median 19.8 ms. On this 11-document corpus, embeddings did not raise the hit rate. They added latency.

Where Cursor is already enough

For the two facts that already live in tech-demos, both systems hit. Workspace ripgrep median was 5.5 ms. WeKnora median was 62.6 ms, about 11× slower. Mid-chat, Cursor should keep grepping the open repo. Pointing those questions at WeKnora does not improve speed or accuracy.

Where the index helps

Nine facts are outside this workspace (other public repos, plus the calendar digest). Workspace search missed all nine. WeKnora hit all nine in about 59 ms once the index was warm. That is the gap an agent feels: the Spanish app is habla-spanish, orbitdiff watches Instagram follows, mstudios-react ports mstudios.cc, the GitHub account dates to 2024-12-11, the logo skill checks SVG, the recurring meeting is Mstudios Sync, the Cancun–Atlanta flight is DL 609, and the Murph meetup is at The Goodtime Hotel starting 2:45pm.

A live GitHub walk for the Spanish-app question (list repos, then download READMEs until the text matched) took 352 ms and 2 README downloads. One known README download was 76 ms. Warm WeKnora search was faster than discovering the file on GitHub, and the agent does not have to know the repo name first. The cost is paid earlier: someone has to copy those documents into the knowledge base. WeKnora did not see GitHub or Calendar until this test uploaded them.

Cursor already has GitHub and Google Calendar tools on this account. Those tools return live data with no ingest step. WeKnora is an extra index in front of a snapshot, not a replacement for those connectors. It wins on repeat questions over a corpus you chose to file, especially once that corpus is larger than a handful of READMEs.

Cold start is a different number

While the reparse was still embedding, the first hybrid searches took 11.0 s and 27.0 s. After the model and index were warm, the same questions sat under 75 ms. The first question in a quiet session can look slow even when the steady state is fine. A 0.5B local embedding call is part of that first-hit cost.

Asking WeKnora to answer, not just retrieve

Three questions were sent through real /knowledge-chat with qwen2.5:0.5b after retrieval was working. Time to the first streamed byte was about 110 ms (the tool call starts quickly). The finished answers were wrong.

Memory

Inside one chat

The session was told: “the October demo code name is Harborline.” The next turn asked for that code name. WeKnora answered sv-agentation-playground, a slug from the bookmarks file it had just retrieved. The prior user sentence was ignored. That is worse than Cursor’s normal thread, which still has the previous message in context. Elapsed time: 4.6 s to store, 6.9 s to answer.

Across chats

Workspace memory starts off. Turning on only the personal switch left effective: false and POST /memory/items returned “memory is disabled.” After PUT /tenants/kv/memory-config with enabled: true, a preference was stored:

Marquis wants agents to measure retrieval latency against workspace search before claiming a knowledge demo works.

A new session asked that question. The item’s use_count went from 0 to 1, so WeKnora did attach the memory to the turn. The 0.5B answer still did not repeat it. Notion memory for this account is empty, so Cursor has no competing long-term note. WeKnora’s store works. With this model it did not change what got said.

Write mode was explicit_only. The product will not silently learn from chat until an admin sets auto-extract. That default is safe, and it means “it remembers what I said yesterday” is not true until someone turns the workspace switch on and the chat model is strong enough to read the injected note.

What to do with this in Cursor

  • Keep repo questions on Cursor’s own search. WeKnora was slower and no more accurate.
  • Use WeKnora when the passage is filed in a knowledge base and is not in the open workspace. Warm lookup was ~59 ms and 9/9 on those questions.
  • Do not route the final answer through a 0.5B local model. Hand the chunks to the Cursor model. That is the path that matches how you would use RAG mid-chat.
  • Calendar and GitHub connectors you already have are the live source. WeKnora only knew those facts because this test pasted them in.
  • Turn on workspace memory before expecting cross-chat recall, and judge recall by the answer, not by the row existing. Here the row existed and the answer still missed.

Limits of this measurement

Eleven documents. Keyword search was enough, so this does not show a win for vectors. A corpus of thousands of pages could reverse the keyword-vs-vector result and push latency up. No reranker was configured. The chat model was the smallest Qwen that fit on CPU, not a frontier model. Cold numbers include the embedding backlog from a failed-then-retried parse.

Stack: WeKnora 0.8.2, ParadeDB, Redis, docreader, Ollama nomic-embed-text + qwen2.5:0.5b. API health was {"status":"ok"}. Raw timings: warm hybrid search, five repeats, median reported.
